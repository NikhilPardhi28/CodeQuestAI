# PostgreSQL CI schema migration fix

The `postgres-integration` Actions job sets `CODEQUEST_TEST_DATABASE_URL` to its PostgreSQL 17.5 service database, `codequest_test`. The migration integration test and both concurrency tests read that variable. They build Alembic configuration with the absolute repository `Database/migrations` script location and set the Alembic URL from the same environment value. The authoritative migration command is `uv run python -m alembic upgrade head`; tests call the equivalent Alembic Python API. Each test runs the migration before seeding, and seeding before catalog queries.

The proven root cause was transaction nesting in `Database/migrations/env.py`. The PostgreSQL branch executed `SET TIME ZONE 'UTC'` on a SQLAlchemy 2.x `Connection` before Alembic's `context.begin_transaction()`. SQLAlchemy autobegins a transaction for that statement. Alembic then ran its migrations inside a nested transaction; its log reported all three revisions, but the outer transaction remained open. Exiting `with connectable.connect()` closed the connection and rolled back that outer transaction, undoing the DDL and `alembic_version` update. SQLite did not execute the PostgreSQL-only `SET TIME ZONE` statement, so its migration tests did not expose this behavior.

The correction commits the session-level timezone statement before calling `context.configure()` and `context.begin_transaction()`. Alembic now owns the top-level migration transaction, which its transaction context commits. No migration DDL, schema selection, URL, seed order, or test assertion was changed.

The tests continue to emit `POSTGRES_MIGRATION_DIAGNOSTIC` records before and after upgrade. Records show sanitized engine, Alembic, and environment URL targets; target equality; `current_database()`, `current_schema()`; Alembic current/head revisions; and whether `curriculum_regions` exists. No user, password, or URL query values are logged. After upgrade, the SQLAlchemy test engine is disposed and recreated before diagnostics and seeding, so the check uses a fresh connection. A failing assertion stops before seed/query and reports the actual migration state.

The GitHub Actions job enables pytest output capture bypass (`-s`) so these records remain visible for verification. The expected post-upgrade diagnostic is `alembicCurrent == alembicHead` and `curriculumRegionsExists == true` in `codequest_test.public`. The new CI run is still required to confirm the correction against PostgreSQL.

The SQLite HTTP fixture creates ORM metadata directly with `Base.metadata.create_all`, then seeds. The SQLite migration round-trip uses Alembic against a temporary file database. Neither path establishes PostgreSQL migration or concurrency behavior.

Local PostgreSQL reproduction remains blocked because `CODEQUEST_TEST_DATABASE_URL` is not configured. SQLite migration tests validate the unaffected SQLite path only. Run the actual `postgres-integration` job and inspect its diagnostic output before claiming the fix is effective.
