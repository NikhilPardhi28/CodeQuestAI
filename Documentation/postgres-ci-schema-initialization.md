# PostgreSQL CI schema diagnostics

The `postgres-integration` Actions job sets `CODEQUEST_TEST_DATABASE_URL` to its PostgreSQL 17.5 service database, `codequest_test`. The migration integration test and both concurrency tests read that variable. They build Alembic configuration with the absolute repository `Database/migrations` script location and set the Alembic URL from the same environment value. The authoritative migration command is `uv run python -m alembic upgrade head`; tests call the equivalent Alembic Python API. Each test runs the migration before seeding, and seeding before catalog queries.

The previous preflight attempted to reset an Alembic version stamp, but the CI rerun still failed. That hypothesis is not treated as established and the destructive reset was removed. The tests now emit `POSTGRES_MIGRATION_DIAGNOSTIC` records before and after upgrade. Records show sanitized engine, Alembic, and environment URL targets; target equality; `current_database()`, `current_schema()`; Alembic current/head revisions; and whether `curriculum_regions` exists. No user, password, or URL query values are logged. After upgrade, the SQLAlchemy test engine is disposed and recreated before diagnostics and seeding, so the check uses a fresh connection. A failing assertion stops before seed/query and reports the actual migration state.

The GitHub Actions job enables pytest output capture bypass (`-s`) so these records are visible in CI logs. The next run should establish whether the configured URL targets differ, Alembic sees the expected migration scripts, the current schema is unexpected, the revision is not at head, or a fresh connection cannot see the table. The supplied error snippet alone does not distinguish these cases, so no root cause is claimed until those diagnostics are observed.

The SQLite HTTP fixture creates ORM metadata directly with `Base.metadata.create_all`, then seeds. The SQLite migration round-trip uses Alembic against a temporary file database. Neither path establishes PostgreSQL migration or concurrency behavior.

Local PostgreSQL reproduction remains blocked because `CODEQUEST_TEST_DATABASE_URL` is not configured. Run the actual `postgres-integration` job and inspect its diagnostic output before claiming the fix is effective.
